# Petal Web Client (web-harness)

A browser-based Petal client: join a meeting by code, share a real
screen/window/tab, see everyone else's shares and webcams as tiles, and talk
over a real microphone — a real Nth participant for people without the
native app. The UI uses the desktop app's approved design tokens and fonts,
so it reads as Petal, not as a test page.

It began life as (and still doubles as) the repo's browser test harness: the
synthetic test modes automation depends on — a canvas test-pattern "shared
window" and a 440Hz tone "microphone", neither of which needs a permission
prompt — are kept as first-class options in the **Developer & test tools**
drawer at the bottom of the meeting screen.

It is standalone — not part of the shipped Petal app, not built by
`apps/desktop`'s Tauri build, and not linked from it.

## Run it

From `web-harness/`:

```sh
npm install   # first time only
npm run dev
```

Vite prints a local URL (port 5184 if launched via `.claude/launch.json`'s
`petal-web-harness` configuration). The same dev-server process hosts the
token-minting endpoint (see below) — there is no second process/port.

To run against a local `livekit-server --dev` (`ws://localhost:7880`,
`devkey`/`secret`) when `apps/desktop/.env` is missing or points elsewhere,
set the env vars in the shell (dotenv never overrides already-set vars):

```sh
LIVEKIT_URL=ws://localhost:7880 LIVEKIT_API_KEY=devkey LIVEKIT_API_SECRET=secret npm run dev
```

## Using it

1. **Join screen:** enter your name and either a meeting code (`eng-sync`)
   or a full pasted invite link — both `petal://join/<code>` (the native
   app's invite format) and this client's own
   `https://<host>/?code=<code>` links parse correctly
   (`src/joinInput.ts`). Unrecognized URL shapes get a clear inline error
   instead of silently joining a room literally named the URL. Or click
   **Create a new meeting** for a fresh generated code.
2. **?code= auto-join:** opening `http://<host>/?code=<room>` prefills and
   joins immediately — this is the link the **Invite** control copies.
3. **Meeting screen:** a tile grid (one tile per participant, plus a
   separate tile per screen share) and a bottom control bar with circular,
   feature-labeled controls:
   - **Audio** — real microphone (`getUserMedia({audio})`). First click
     publishes; later clicks toggle mute/unmute via LiveKit's
     `LocalAudioTrack.mute()` (no unpublish). Red + slash = off/muted.
   - **Video** — real webcam, published as `petal-camera-<identity-slug>`
     (H.264) — the native compositor renders it as its own window.
   - **Screensharing** — real capture via `getDisplayMedia` (the browser
     shows its own window/tab/screen picker), published under a fresh
     `petal-window-<random u32>` name with H.264 forced. Green = live.
   - **Invite** — copies the `?code=` join link, confirms with a toast.
   - **Leave** — disconnects and returns to the join screen.
4. **Developer & test tools** (collapsible drawer, closed by default):
   Network diagnostics (nested, also closed by default), the synthetic
   test-pattern share + 440Hz tone, raw state readouts, and the live
   session log (connection / participant / track lifecycle, newest first).

Browser reality check: remote shared windows CANNOT be independent movable
native windows in a browser — they render as tiles in the grid. That native
window magic remains exclusive to the desktop app's compositor.

## Meeting codes and the LiveKit room name

The join value is a capability credential, not just a human room name:
`<readable-label>-<32 lowercase hex chars>` (for example,
`design-review-0123456789abcdef0123456789abcdef`). The readable label is for
humans; the hex suffix is the authorization boundary. A bare guessable label
such as `design-review` is invalid for token minting.

Both this client (`src/meetingCode.ts::livekitRoomName`) and the native app
(`apps/desktop/src-tauri/src/rooms.rs::livekit_room_name_for`) map the full
credential to the canonical LiveKit room name `petal-room-<credential>`.
Typing or pasting the same full credential into the native app and this
client therefore lands both in the same LiveKit room.

**The credential parsing and room-name mapping MUST stay in lockstep across
native, web, and backend.** `tests/contracts.test.ts` pins these vectors.
Codes generated by **Create a new meeting** keep the readable three-word
prefix but append the required capability suffix.

## Token endpoint

The browser asks `POST /api/token` with the human meeting code and identity,
then connects with the returned `{ url, token, room }`. In deployed testing,
set `VITE_PETAL_BACKEND_URL=https://app.petal.live` so the harness
uses the real backend from `../backend`.

For local-only dev with no hosted backend, a Vite middleware
(`server/tokenPlugin.ts`, wired in via `vite.config.ts`) implements the same
POST shape on the dev server. It reads `LIVEKIT_URL` / `LIVEKIT_API_KEY` /
`LIVEKIT_API_SECRET` from `apps/desktop/.env` in Node, not in browser JS. The
browser only receives the signed JWT and LiveKit URL.

## Wire-format contracts (must match the native app)

All unit-tested in `tests/contracts.test.ts` (`npm test`, runs via
`node --test` with Node's native TS type stripping):

- **Window shares:** track name `petal-window-<window_id>` —
  `apps/desktop/src-tauri/src/transport/publisher.rs::track_name_for_window`,
  inverse `window_id_from_track_name` in `compositor.rs`. If the format
  drifts, the native side silently ignores the share. Real screen shares
  use a fresh random id per share, kept below `0x8000_0000` (the native
  side reserves the high bit for camera-derived synthetic window ids); the
  test pattern uses one random 6-digit id per page load.
- **Webcams:** track name `petal-camera-<identity-slug>` — the native side
  hashes the full track name (fnv1a | 0x8000_0000) into a synthetic
  compositor-window id.
- **Telepointers:** topic `petal.telepointer`, JSON
  `{windowId, userId, x, y, visible}` (x/y normalized 0..1) —
  `apps/desktop/src-tauri/src/telepointer.rs` (SPEC.md §4.5). While the
  test pattern is shared, an animated sender broadcasts a gliding cursor
  so the native pointer overlay can be verified. When viewing a remote
  window share tile, browser pointer hover/leave events publish the same
  lossy telepointer contract so the native sharer can see the web viewer's
  pointer over the shared window.
- **H.264 is load-bearing, not a preference:** the native receiver-side
  compositor (`native_display.rs`) only renders frames that decode to a
  Native CVPixelBuffer — on macOS, a VideoToolbox-HW-decoded **H.264**
  stream. VP8/VP9/AV1 decode to software I420 and hit a deliberate
  no-render fallback: the share never appears as a native window. Every
  video publish here forces `videoCodec: 'h264'`, and after each publish
  the ACTUAL negotiated codec is read back from WebRTC outbound-rtp stats —
  a non-H.264 result logs a loud error in the session log and is recorded
  on `window.__petalHarness.codecChecks` for automation.

## Why the synthetic test modes stay

Real `getDisplayMedia` / `getUserMedia` capture requires a browser
picker/permission prompt that unattended automation (Chrome DevTools MCP)
cannot click, and ties test health to host hardware/permissions. The canvas
test pattern (`canvas.captureStream(30)` — deterministic moving pattern with
a live frame counter) and the 440Hz oscillator tone (a real
`MediaStreamTrack`, indistinguishable to LiveKit from a mic) need no
prompts and are deterministic — reliably drivable by automation, which is
what the repo's end-to-end verification depends on. Do not delete them.

## Test/automation hook

`window.__petalHarness` exposes `{ room, localVideoTrack, screenTrack,
micTrack, codecChecks }` for browser-driven verification (codec/stats
checks). Test-only; never shipped in the real app.

## Files

- `index.html` — join screen, meeting screen (topbar / tile grid / control
  bar), dev drawer, toast.
- `src/main.ts` — all client logic: LiveKit connect/publish/subscribe, tile
  rendering, control bar, real media (screen/mic/webcam), synthetic modes,
  telepointer sender, codec verification, session log.
- `src/trackNames.ts` — track-name + telepointer wire-format contracts.
- `src/toastMount.ts` — mounts the SHARED Svelte `<Toast>` component
  (`shared/ui/components/Toast.svelte`) into `#toast`.
- **Shared package** — design tokens (`shared/ui/tokens.css`), presentational
  components (`shared/ui/components/`), and meeting-code / join-input /
  local-echo logic (`shared/logic/`) are the SINGLE SOURCE imported by both
  this client and the desktop app via the `@petal/shared` alias — never copy
  them into `web-harness/src/`.
- `src/fonts.css` + `src/assets/fonts/` — self-hosted Manrope / Albert
  Sans / JetBrains Mono variable fonts from the design bundle.
- `src/style.css` — the web client's styling on top of the shared tokens.
- `server/tokenPlugin.ts` — dev-server token endpoint (see above).
- `tests/` — contract + join-input unit tests (`npm test`).
